# Delivery Summary — pr-fixer rule

plan: `pr-fixer-rule` · run: `partial` · date: `2026-10-06` · updated: `2026-10-10`
baseline: `devague summary skeleton`

## Intent

> A new PR in any AgentCulture repo is picked up by a fixer agent that drives it to green: SonarCloud gate, failing checks and unresolved review threads fixed on the PR branch, never merged

After: A same-repo PR in any agentculture repo gets a fixer run on spark2 without anyone asking: the agent fixes Sonar issues, failing checks, and review comments from the operator, Qodo and a pre-approved list of users and apps (comments from anyone else are ignored) in a worktree; the engine's tests gate each commit, the App pushes passing commits, and the operator only reviews and merges

- `d28` — Shared, first-come-first-served queue per model server (#35): an optional actor param concurrency_pool shares one slot count across every actor naming it (cap on the pool); a waiting step takes a ticket stamped at its first 'blocked' and only the oldest live ticket is admitted; queue_timeout counts from the head of the queue, so a deep queue delays but never fails a run. The queue is visible: the engine records each waiting run's position and emits rules.queue.changed when positions move (any rule or workflow may react, non-agentic), and the PR status comment gains an 'In queue' stage before 'Agent' reading 'Nth in line (behind `<repo>#<n>`)', updated as the queue moves; the status board stays the comment's only writer. Actors without a pool behave as today; token budgets stay per actor. — Operator, 2026-10-10: 'Qwen shouldn't split its attention' then 'And confirmed, shared pool, issue and next in priority'; then 'we need a proper way to signal that fixer is busy. We need to add a 'in queue' step, and a message of count in line that updates.' and 'It can be non-agentic seperate workflow, even'. Live case: irc-lens#62's run waited behind culture-rules#37's with no sign on the PR.
- `d29` — Amends d28: the fixer's queue is owned by two visible, non-agentic rules, not engine-internal tickets. (1) Add to queue: the four fixer trigger rules (checks settled, comment, review, review comment) no longer start pr-fix directly; their workflow appends the request (repo, PR, head, trigger data) to a durable queue for the pool and replies with its place in line. (2) Progress queue requests: on a queue add, or when a pr-fix run ends (succeeded, failed, superseded, cancelled), a workflow takes the oldest live request when the pool has a free slot and dispatches it (an event a pr-fixer-dispatch rule turns into the pr-fix run, keeping the PR's concurrency key and 3-attempt budget), then refreshes every waiting request's position. The status comment shows 'In queue: Nth in line (behind `<repo>#<n>`)' from the queue, the status board staying its only writer. The engine keeps only the concurrency_pool cap as a safety net; a request whose PR closed or whose head moved is dropped at dispatch. — Operator, 2026-10-10: 'Add to queue rule, progress queue requests rule.', then chose 'Two rules own the queue': the queue is part of the product model (rules -> workflows), visible and editable in the editor, rather than hidden engine state.
- `d30` — Amends d29: a retry waits in the queue. A pr-fix run makes one try (agent then gate) and frees the pool's slot; a try that does not pass (gate fail or guard, or the review's request_changes) re-enters the queue at the back as a retry, carrying the gate's or the reviewer's instruction and the PR's attempt count, so the other queued requests run first and the retry runs when it reaches the head again. The PR's 3-attempt budget counts across these requeues; a third failed try hands back as today. A newer request for the same PR (a push or /fix) replaces the queued retry and keeps its place. — Operator, 2026-10-10: 'Retry should sit in queue, so if it failed, it goes to the other items in queue, when done, returns to retry'. Live case: culture-rules #37's run held the single Qwen slot through tries 2 and 3 while irc-lens #62's run waited blocked.
- `d31` — Merge from base: the fixer may resolve a PR's conflict with its base branch. One merge commit by the App's commit_author whose second parent is already on the PR's base branch (reachable from the base ref at gate time) is allowed: the diff guard's merge_commit rule and github.push's foreign_author check exempt that merge's second-parent history (the base's own commits) and nothing else; every other new commit must still be the bot's. The diff guard, the test gate and the review judge only the merge's own resolution (its diff against both parents), never the base's commits. A PR that turns CONFLICTING starts a fixer request like checks settling does. — Operator approved 2026-10-10 ('approved: the merge-from-base allowance, for when the fixer itself should resolve conflicts like #37's'). Live case: culture-rules #37 run-4f297da0 — Qwen merged origin/main and resolved the three version files correctly (f6f91ef), and the diff guard rejected it (merge_commit); the push guard would also have refused foreign_author.
- `d32` — A new request is a new story: the 3-try budget belongs to one request, not to the PR forever. Besides today's resets (a human push, checks settled green), a trusted /fix or @rules-culture-dev comment (or review comment) resets the PR's attempt budget when it fires, through a generic rule flag resets_attempt_budget (set on pr-fixer-comment and pr-fixer-review-comment), not a hard-coded comment check. A queued retry (d30) belongs to its story: a new request replaces it in place with a fresh budget. — Operator, 2026-10-10: '3 try budget per attempt. So if I add another /fix or push update it's a new story'. Today _resets_budgets (node/firing.py) resets only on a human push or green checks, so a /fix after three failed tries is refused.
- `d33` — sonar.gate_issues on a passing gate no longer forbids Sonar work outright: it also returns the issues on the PR's own new code (never the project backlog), and its note says the gate passes and to fix a Sonar issue only when the trusted request names it, never the backlog. A bare /fix on a passing gate still leaves Sonar alone; a /fix naming a new-code issue gets it as data. — Operator approved 2026-10-10 ('please do'). Live case: irc-lens#62's /fix asked for S9073 in tests/test_mail.py; sonar.gate_issues said 'The SonarCloud quality gate passes (OK): do not work on Sonar issues.', so Qwen made no commit (run-6a89ec0d, no_changes); on lobes-cli#303 the same note was overridden by the comment, so the outcome depended on the model.
- `d34` — Cancelling the fixer: a trusted author stops a PR's fixer story with a /stop comment (or @rules-culture-dev stop), or a thumbs-down reaction on the /fix comment or on the fixer's status comment. GitHub sends no webhook for reactions, so while a story is active or queued the node polls those two comments' reactions about once a minute and emits github.reaction.added. A pr-fixer-stop rule (non-agentic workflow) cancels the PR's active fixer run (no push, no hand-back), removes its queued request and retries, and ends the story ('Stopped by @user'); the next /fix or human push starts a new story. Built after #35. — Operator, 2026-10-10: 'We need a form of cancellation, like reacting thumbs-down on the /fix request to stop the agent's work / retries'.
- `d35` — One status comment per story, carried through the queue: the story's status record (and its comment) is passed on from the request that started it (queue-add) through every dispatched try and requeued retry, so each try updates the same comment instead of posting a new one; the story ends the comment once (pushed, handed back, stopped). Only if the status record cannot be carried through the queue is a temporary comment per try accepted, until Boards (#38). The new pr-fix digest is approved by the operator. — Operator, 2026-10-10: 'Status comments - no, I don't want to spam with comments. We can manage the same comment properly. We need to pass it on. If we can't, then a temporary noise is approved.' and 'pr-fix fingerprint approved'.
